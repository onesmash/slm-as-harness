## 填表规矩

- **性质一句话**：必须能被反例证伪。写「视图逻辑正确」不合格，写「视图恒等于帐本最后 60 条」合格。
- **owner**：一个人。模型、测试、运行监控引用的是**同一句原文**，不是三种转述。
- **范围**：`守住` 必须限定范围（单写者 / 单进程 / 仅旧版本数据 / 仅窗口内 60 步…）。**不写范围的「守住」等于过度承诺**，比写「未判定」更糟。
- **证据等级**：**只允许 `L1` / `L2` / `L3`，或不建模的固定写法**（见下一条）。`L1` 只有模型（S1）｜`L2` 模型 + 反例回放 + 守门测试（S1+S2+S3）｜`L3` L2 + 真实日志（S4，必须落在 `S4 日志` 列且有 `PASS`）。等级写清，读者才知道这条「守住」覆盖到哪一层；**写了 L3 却没有 S4 的 PASS，机器核对会直接报错**。别写「TLA+/TLC 建模」这类描述——它不是等级，还会让等级那道机器门整列失效（自由文本永远匹配不到 `L3`）。
- **破坏变体 / 证据命令**：写清改哪一行、跑哪条命令。没有破坏变体的性质，状态一律 `未判定`（从没见过失败的检查证明不了它有分辨力）。
- **退出码**：**真实跑出来的那个数**，不是预计的。注意两套：`statechart` 违规归一化成 `1`；裸 `tlc2.TLC` 不变量违反 `12`、时序性质违反 `13`。日志校验器 `UNDECIDED` 是 `2`，它既不是通过也不是失败。
- **状态**：`守住` 需同时满足 见过失败 + S3 绿 + 范围写清；S4 未过的行最高记 `L2` 并写清日志缺什么。
- **不建模的性质**：证据等级写固定格式 `不建模：<理由>；由<谁>覆盖`（例：`不建模：数据形状问题；由纯函数测试覆盖`）。**必须写清谁覆盖**，机器核对会查这一项；**不许留空**——留空看起来像漏做。
- **sync commit**：模型与代码对齐时的 commit，**S5 才填**。S0 建表时这一列写「基线」的 commit（这次改动从哪个版本开始），或先空着；别在 S0 阶段伪造一个还不存在的对齐点。代码改了但没重跑，标 `pending` 并写差在哪。**机器核对会拿这一列与「覆盖的文件/函数」对 git 核**：覆盖文件在这个 commit 之后被改过（含未提交改动）就报错——那说明这条「守住」描述的是过去的代码。
- **承诺变更证据**：**只有当性质本身有意改写时**才填，写成 commit 或可打开的文件（设计文档 / 测试 / changelog）。机器核对会查它指不指得到东西；先把措辞改成能通过、再补一条「证据」的，按假通过处理。
- **只允许一张表**：表格中间出现空行再接表格行，机器核对会报「表格中断」——它上一次就是这样把 19 行读成 9 行、还判了 OK。

## 收口三句话（写进 README）

1. 这条性质是什么（一句人话）
2. 哪条命令能重跑（含环境变量，从干净 shell 可跑，从零到通过要跑几次）
3. 覆盖到哪个 commit，哪里没覆盖

三句写不出来 = 没到 S5。
