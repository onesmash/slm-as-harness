# 七条质量门：当 S5 的验收契约

抄自 pstack `create-formal-verification-skill` 的七条门（读于 `cursor/plugins` main 分支，2026-11-22；上游仓库 `license: null`，此处为改写自用，不转发原文），改写成能当场问的问题。每一条都可以答「没有」——答「没有」就必须写进交付物的范围声明，而不是含糊过去。

| # | 门（原文关键词） | 当场怎么问 | 不合格的样子 |
|---|---|---|---|
| 1 | **True to the code** | 每个模型动作，能当场打开对应代码吗？模型的一步 = 代码的一步？ | 模型里有一个真实代码没有的抽象动作 |
| 2 | **Able to fail** | 这条性质见过的失败是什么？破坏变体的 diff 在哪？ | 从没红过；或红了但理由是编译错 |
| 3 | **Findings stay findings** | 代码真违反了，你敢报吗？ | 把性质削弱到能过、改断言迁就实现、未经允许改产品代码 |
| 4 | **Honest about scope** | 界、假设、left-outs 全写了吗？ | 只写「已验证」，不写常数多大、哪条路径没覆盖 |
| 5 | **Readable without the tool** | 性质能不能一句话讲给人听？反例能不能讲成步骤序列？ | 只有 TLA+ 原文，没有一句人话 |
| 6 | **Cheap to rerun** | 一条命令？工具版本钉了吗？短到下一个 agent 愿意每次跑吗？ | 要手工装环境、要改路径、跑 40 分钟 |
| 7 | **Kept in step with the code** | 覆盖的文件/函数与本次确认的 commit 记了吗？ | 代码改了，模型和登记表还停在旧 commit |

## 三条最容易被跳过、代价最大的

- **第 2 条**：没有失败过的检查没有分辨力。这条不是流程洁癖——破坏变体是唯一能证明「检查器看得见」的手段。
- **第 3 条**：模型检查最危险的结果不是「报红」，而是「为了让 CI 绿，把性质改弱」。性质一弱，后面所有证据都是假的。**代码违反性质就报，不许把性质或模型削弱到能过。**
- **第 7 条**：没有 sync commit 的验证会静默过期。过期比没有更糟——它给人一种「有门」的错觉。

## 与三条判据技能 + 一个画图工具的分工（别复述，直接调）

| 场景 | 调哪个技能 |
|---|---|
| 要宣布「做完了」之前 | `principle-prove-it-works`：验真东西，不验代理指标、自述、「编译过了」 |
| 要报任何数字（状态数、加速比、覆盖率） | `principle-explain-the-number` + `benchmark-checklist`：先命名限制，再排除「测的不是那件事」 |
| 发现自己第二次写同一条提醒 | `principle-encode-lessons-in-structure`：改成 lint / 元数据位 / 运行时检查 / 脚本 |
| 要画状态图给人看 | `statechart` |

## S5 交付检查表（逐项打勾才算收口）

- [ ] 每条性质：一句话、owner、覆盖的文件/函数、sync commit
- [ ] 每条性质：破坏变体的 diff + 报红输出（贴原始输出，不转述）
- [ ] 一条重跑命令，含环境变量，从干净 shell 可跑
- [ ] 每条性质的当前状态：守住 / 报红 / 未判定（「未判定」不许写成通过）
- [ ] 范围声明：界、假设、left-outs
- [ ] 代码改了但模型没改 → 标 pending，并写清差在哪
