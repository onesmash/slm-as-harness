# 五站逐站：动作、证据形态、常见假通过

S0 是前置筛选，不算一站；S1–S5 是五站。每站只有一个出口判据，不满足就不许进下一站——**跳站的代价不是在后面补，而是后面全部失真**。

---

## S0 选点（前置，不算一站）

**只挑「坏了最贵 × 测试最摸不到」的性质。** 两个条件缺一不可：

- 坏了最贵：数据损坏、不可恢复、要人工修、外部可见
- 测试最摸不到：正常路径跑一遍看不出来；要特定顺序、特定重启时机、特定并发交错才触发

**出口**：每条性质一行，写清一句话、一个 owner、覆盖的文件/函数、sync commit。用 `templates/property-register.md`。

**常见假通过**：把「我知道这段代码干什么」写成性质。真正的性质必须是**能被反例证伪的一句话**，比如「视图恒等于帐本最后 60 条」，而不是「视图逻辑正确」。

---

## S1 建模

**顺序不能倒：先画图让人确认转移对不对，再写模型（PlusCal 或手写 TLA+）。**

1. 图（Mermaid / `statechart`）先给评审看——状态名字用读者的话，不用变量名
2. 两条路都行：PlusCal 写算法再翻译（多实例进程用 `process P \in {1,2}`，**不写括号**，见 `examples/param-process/`），或直接手写 TLA+ 加显式 `pc`（`examples/liveness/`）
3. `Next` 写成各动作的析取，否则 TLC 把每一步都叫 `Next`
4. 终态要有动作（`Done == pc \in {...} /\ UNCHANGED vars`），否则终态被判成死锁

**出口判据（三条全要）**：

- ① **见过它失败**：每条性质配一个破坏变体，且**亲眼**见它报红
- ② 反例能读成人话的步骤序列（不是一串变量赋值）
- ③ bounds 写清：常数取多大、为什么够、`CONSTRAINT` 卡在哪

**证据形态**：`.tla` / `.cfg` / `chart.mmd` / 反例轨迹（`report.md` 里的 shortest path）+ 破坏变体的 diff + **图确认记录**（确认人 / 日期 / 那一版图，写在验证记录的 A 分区）。没有这一行，就等于没做过「先画图让人确认」。

**活性性质（`[]<>` / `<>[]`）的破坏变体不一样**：不要改逻辑，抽掉公平性——`Spec == Init /\ [][Next]_vars /\ WF_vars(Next)` 去掉 `WF_vars(Next)`，TLC 就能给出「永远 stutter」的反例。活性性质在 `.cfg` 里写 `PROPERTY`（不是 `INVARIANT`）。可跑例子：`examples/liveness/`。

**常见假通过**：

- 一次都没红过 → 证明不了这条检查有分辨力（最贵的一种假通过）
- 把规则削弱成恒真式：只断言单个变量取值合法（`view \in {"empty","fresh"}`），不把它与第二个变量关联——这样它几乎不可能被违反，也就什么都证明不了
- bounds 大到没跑完，却说「没有反例」
- 模型里塞了只有模型才有的抽象动作，真实代码里没有对应调用
- 图是模型写完之后补画的：顺序反了，「人确认」就退化成橡皮图章；图与模型对不上时也不会有任何检查报警（实例：`chart-fixed` 沿用了另一套状态名，图上写着「可见」，模型里那一刻采集器还没落盘）

---

## S2 桥接

**把 TLC 的反例逐步映射成真实调用。** 一步模型动作 → 一行真实调用/一次接口请求。

**出口**：同一条违规在真实代码上有**可重放**的失败用例（先红）。

**复现不出 → 先疑模型**，不是先疑代码：
- 模型动作在代码里没有对应物（抽象过头）
- 模型缺了一个代码里存在的交错（抽象不足）
- 性质写的不是代码语义（最常见：模型里 view 是变量，代码里 view 是每次现算的函数）

**工具**：fast-check `commands`（命令序列 + shrink + `seed / path / replayPath`）｜Quint MBT（模型出轨迹 → 驱动真实代码回放）

**常见假通过**：拿一个手写的单测冒充回放——它复现的是你以为的 bug，不是 TLC 报的那个 bug。判据是：**把反例里的每一步都指出来，一步不缺**。

---

## S3 守门

**按 `ub-mode` 做**：先写会失败的测试，亲眼看它按预期理由失败，再让它变绿。

**出口判据（三条全要）**：

- ① 红是**预期的那个理由**（不是语法错、不是 import 失败、不是超时）
- ② 变绿
- ③ **把被测单元换成失效实现，这条测试必须仍然失败**——否则它断言的是「东西被调用了」，不是「行为对了」。按被测对象的形状选一种失效法：函数 → `return undefined`；生成器 → 输出空文件 / 空字符串；接线 → 不注册；词典 → 删一条。判据是「失效了就必红」，不是必须写成某一行代码（源头：ub-mode 的 "if the test would still pass when every function returned nothing, throw it out"）

**证据形态**：提交信息写 why / what / how proved；测试文件里保留断言的可读失败信息。

**常见假通过**：红是「模块找不到」｜断言写成 `expect(true)`｜把断言放宽到「不抛异常」｜mock 掉了被测逻辑本身。

---

## S4 上线

**用规格校验真实日志（不需额外埋点），或断言常开。**

**出口**：能报出**模型未覆盖**的行为；报出即回 S1 改模型。

**两个必须写进报告的东西**：

- 日志够不够细（trace validation 的假通过：日志不全时可能被错误接受，极端情形只记录执行长度也能「通过」）
- 失败时**在哪一步**对不上（它给不出单条反例，只能给一条最大有限行为，所以「反例见附件」是废话）

**本机可直接用的骨架**：`examples/log-check/check-log.mjs`（无依赖，Node 跑）。它给三个判定与三个退出码：`PASS`=0、`FAIL`=1（指到步号+字段+expected/logged）、`UNDECIDED`=2（缺字段）。**`UNDECIDED` 不许写成通过**，也不等于失败——处置不同：一个是补日志，一个是修代码。

**常见假通过**：只看「通过」不看日志粒度｜把「日志不足以判定」当成通过（这是「未判定」，要单独标）｜断言只在正常路径开，异常路径关掉｜拿日志里的状态回灌继续往下推（等于让日志自己给自己作证）。

## S5 收口

**三句话 + 覆盖记录 + 一条命令。**

**出口**：下一个人不看对话，能：

1. 用一条命令重跑
2. 看到每条性质的当前状态（守住 / 报红 / 未判定）
3. 看出覆盖到哪个 commit；代码变了，登记表标 pending

**证据形态**：README（或登记表）+ sync commit + 完整命令（含 `TLA2TOOLS`/`JAVA` 这类环境变量），以及一次**机器核对**：`node <skill>/scripts/check-register.mjs <property-register.md> --root <仓库根>` 的 exit 0。这道核对只验「表读得进来 + 证据指得到东西」，**不执行命令**；`--strict` 才把风格类 WARN 也算失败。人眼核对不算核对。

**「一条命令能重跑」的六条判据**（①–④ 是核心，⑤⑥ 是延伸；每一条都在真实项目里翻过车）：

1. 干净 shell 能跑——不是「在我的 shell 里能跑」。
2. **不依赖宿主已占用的环境变量名。** `DSH_HOME`、`HOME`、`CI`、`PATH` 这类名字常被宿主或 CI 预置；脚本用 `${DSH_HOME:-...}` 就会静默指向错的目录，并把「找错目录」报成「数据不足（UNDECIDED）」——这比直接报错更糟，因为它把工具故障伪装成业务结论。
3. 贴**真实退出码**，并注意一个项目里可能有两套（`statechart` 归一化成 1，裸 TLC 是 12/13）。
4. **从零到通过跑一次就 exit 0。** 需要先建基线再比对的脚本，第一跑出 `exit 2` 是「能解释的」，但不是「可接受的」——正确做法是让脚本自己建基线（试点里改完之后，全新目录首跑就是 `exit 0`），而不是把「要跑两次」写进文档。
5. **证据命令不能只活在聊天记录里。** 贴在群里的命令等于没有：别人照文档验会卡在「先造一个临时目录再软链两边」这种没说出口的前置上。落成仓库里的脚本（自建临时根、清理、退出码透传），文档只引用它。
6. **观察值不算证据。** 步数、行数、条数这类随输入增长的数字，只能记为带时间戳的观察；`守住` 只挂离散判定（退出码、反例有无）。把会漂的数字挂在「守住」下面，等于给承诺加了一个会过期的计时器。

**代码漂移之后：维护循环**（merge、绕过技能的直接改动、以及跨多个提交积累的变化，都要跑一次）

顺序不许倒：**先原样跑一遍，再动模型**。倒过来就会写成「让检查通过」的模型，而不是「描述现在这段代码」的模型。每条检查只许报四类结论之一：

| 结论 | 含义 |
|---|---|
| **in sync** | 覆盖代码没变，检查通过 |
| **updated** | 代码变了，验证已改成描述新代码，检查通过 |
| **bug** | 验证对得上当前代码，而代码破坏了性质——这是关于代码的发现，不是漂移 |
| **blocked** | 拉不回来或跑不起来，写清卡在哪一步 |

一条可以**同时是 updated 和 bug**。每处改动再归四类之一，不许含糊：

- **无影响**：对着模型/harness 判，不是对着 commit message 判（提交信息说「重构」不等于真没动语义）。
- **描述不再对应**：一步拆成两步、分支增删、新路径进入被守卫的状态、取值范围变了。
- **承诺有意改变**：doc comment、测试、changelog、commit message 里**有证据**；性质随之改，并把那份证据填进登记表的「承诺变更证据」列。
- **承诺可能被破坏**：没有任何证据说承诺变了，那么失败按 bug 处理。

改名、拆分、挪到别的文件**仍是被覆盖代码**；新增一个写同一批状态字段的函数也要看。

处置纪律：`blocked` 时不前移 sync commit；验证的更新要单独成一次变更，不与产品修复混在一个提交里；重跑转绿之后，再做一次破坏（删掉新检查或换掉新步骤）确认更新后的检查仍能报红。

**机器侧**：`check-register.mjs` 会把「覆盖的文件」与 sync commit 对 git 核一遍——覆盖文件在 sync commit 之后被改过（**含未提交改动**）就报错；不在 git 工作区或提交写不出来时，输出里明说未核并记 `git_check.checked = 0`，**零样本不算通过**。

**常见假通过**：命令依赖某人 shell 里的 PATH｜「覆盖到这个模块」但没写 commit｜小改代码后没重跑，登记表还写着「守住」｜**旧 pass 是对过期描述的 pass**——更新前通过、更新后失败时，要直说旧描述已经过期，而不是把它当成这次改坏了。

## 成本结构（决定频率，不决定要不要做）

建模是小时级，TLC 是分钟级，桥接是小时级，CI 里的 TLC 是秒到分钟。（这四个量级是经验估算，未在本机按项目实测；用途是决定重跑频率，不是用来报工期。）所以：

- 新性质走**全链一次**
- 之后每次改动只跑：S1 的破坏变体 + S3 的门 + S4 的日志检查
- **代码变了但模型没变**，S5 的 sync commit 就该报警
